## 修复「在线产品 → 父体」查不到数据

**根因（实测逆向确认）**
原站「子体 / 父体」**不是同一个接口换参数**，而是两个完全不同的端点：
- 子体 `POST /api/gw/sellfox/sellfox-product/sellfox/product/pageList`
- 父体 `POST /api/parent/product/pageList.json`

body 里的 `pageType=child/parents` 只是 UI 回显，打到子体端点照样返回子体数据（已实测）。
本项目此前只采了子体端点 → 库内 1640 行 `isVariation` 全为 `'2'`，前端切「父体」按
`isVariation=['1']` 过滤，自然 0 条。

**第二个坑**：父体端点对 `startTime` / `endTime` **有硬性要求** —— 任一为空 `totalSize`
直接返回 0（不是过滤，只是必填）。原站固定传「近7天」区间。

**改动**
- `backend/online_product.py`：新增 `PARENT_LIST_API` + `base_parent_payload()`
  （时间区间默认近7天且兜底非空）；新增 `endpoint_for()/payload_for()`；
  `fetch_count/fetch_page/fetch_all` 增加 `page_type="child"|"parents"` 参数（默认 child，向后兼容）。
- `backend/database.py`：`online_products` 新增 `is_variation` / `parent_asin` 列
  （走 `_MIGRATIONS` 轻量迁移 + 老库回填 `is_variation='2'`）；新增 `get_online_counts()`。
  坑：`CREATE INDEX idx_olp_var` 不能放在 SCHEMA 里，老库会因列不存在报错，必须放 `_migrate()`。
- `backend/api.py`：`crawl_online_products()` 同时采子体 + 父体；`/api/online/meta` 增加 `counts`。
- `frontend/app.js`：`olSetPageType()` 统一维护 `filters.isVariation`；概览显示子体/父体计数。

**结果**：子体 1640 + 父体 135 = **1775**（此前 1640）。与原站 1:1（E1/E1b/H10 通过）。

## ⚠ 重大 bug 修复: 跨天采集导致数据重复、指标翻倍

**现象**：用户在 20:05 点了一次「同步数据」，产品视角本页花费从 ¥43,348.78 变成
¥86,697.56（正好 2 倍），曝光/点击同样翻倍。

**根因**：`ad_records` 的唯一键是 `(tab, scope, biz_key, range_start, range_end)`。
默认查询区间 `endDate = 今天`，跨天后区间从 `08-01~10-04` 变成 `08-01~10-05`，
于是**同一条记录因为区间不同又插了一份**，全库 13950 → 27900。
数据表格看不出来（`get_records` 按区间过滤），但 `get_products()` 读全表 → 翻倍。

**修复（三层）**
1. `database.purge_stale_ranges()`：落库前先删掉该 (页签,维度,店铺) 下**其它区间**的数据；
   在 `crawler.run_crawl` 每个 scope 采集成功后调用。
2. `database.purge_all_other_ranges()`：一次采集**收尾**时再全局清一遍
   （连本次采集失败的维度一起清），保证库里只剩本次快照。
3. `_latest_range()` / `_snapshot_filter()`：`get_products` / `get_product_campaigns` /
   `_term_counts_by_campaign` 只读**最新快照区间**，即使库里有残留也不会重复计数。
   另加 `dedupe_stale_ranges()` 做一次性历史清理（已跑：删掉 13950 行重复数据）。

**接口**：`/api/product/list` 新增 `snapshot: {range_start, range_end}`；
产品视角概览条显示「快照区间 2026-08-01 ~ 2026-10-05」。

**备份**：`data/ads.db.bak_before_dedupe`（清理前）。

**测试**：verify_ui.py 新增 I12b/I12c/I12d（快照唯一性/清理函数/快照区间返回）
+ I21~I24（排序、配色、标题说明、图例）。**全量 102 PASS / 0 FAIL**。

## 产品视角: 表头点击排序 (三级表格)

## 产品视角: 表头「合计」（可累加参数在标题行默认算出总量）

**需求**: 曝光/点击/订单/销售额等可累计的参数, 在标题行直接显示总量。

**做法**
- 表头单元格加第三行 `<span class="th-total">Σ <值></span>`(在「中文 + (英文简称)」下面),
  颜色 `--blue-d` 加粗小字, 排序激活时变蓝。表头行高 38 → 62px。
- `sortableTh(state, o)` 新增 `o.total`(已格式化的字符串)与 `o.totalTip`;
  `totalTip` 写到 **`.th-total` 自己的 title** 上(如「合计：当前查询全部 135 个父体 的花费合计」)。
- ⚠ `bindSortHeaders` 原先把 `th.title` 直接覆盖成「点击排序」, 会把列的说明和合计口径**冲掉**。
  改为 `if (!th.title) th.title = "点击排序"`。
- **一级(产品列表)用后端 `totals`**: `/api/product/list` 新增 `totals` 字段,
  由 `_sum_product_rows(rows)` 在**分页之前**对当前查询的全部行求和 —— 
  表头 Σ 是「全部 135 个父体」的量, 与概览条的「本页花费」是两个口径(都在界面上标清了)。
- **二/三级用前端求和**: 数据已整体载入, `sumBy(rows, field)` 即可; 随过滤口径实时变化
  (搜索词视图: 只看搜索词 花费 ¥728.02 → 全部 ¥1,532.19)。
- **比率列不能相加**: `ctr = Σclicks/Σimpressions`, `acos = Σcost/Σsales`, `cvr = Σorders/Σclicks`
  由 `_sum_product_rows` 重算(实测全库 CTR 0.68%、ACOS 788.86%, 与手工除法一致)。
- 不显示合计的列: 图 / 父ASIN / 父SKU / 子ASIN / 标题 / 操作(非累加量)。
  L3 的「搜索热度」是排名, 求和无意义 → 不给合计。

**实测totals(全量 135 个父体)**: 子ASIN 1640 / 关联活动 587 / 有词活动 86 /
搜索词条目 1130 / 花费 ¥46,258.55 / 曝光 241,353 / 点击 1,635 / 订单 4 / 销售额 ¥5,864
—— 与逐行手工累加**完全一致**。

过滤后 totals 跟随/UI 十个表头有 Σ/非累加列无 Σ/不溢出/与接口一致/tooltip 口径/
排序说明未被覆盖/排序后合计仍在/L2 合计==行和/L3 合计随口径变化)。
