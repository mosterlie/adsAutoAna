# 07 写 · 投放与广告位

> 本页动作全部属 **L1 单值可逆**：改一个数字/状态，秒级可回滚，可自动执行。

---

## ⚠️ 先理解一件事：实际出价在哪一层

自动广告有 **4 个匹配位**，每个位有**独立的 `bid`**。

实测发现：**组默认竞价 ≠ 匹配位实际出价**。

| 活动       | 组默认竞价 | 匹配位实际出价  |
| -------- | ----- | -------- |
| CA_匹克球网  | 13.0  | **20.0** |
| CA_旅行用背包 | 25.0  | **30.0** |
| CA_战术胸挂  | 25.0  | **30.0** |
| CA_排水沟   | 20.0  | 20.0（一致） |

**结论：要真正调价，改 `spTarget/updateBid`（匹配位），不是改组默认竞价。**

稳妥做法：两者都改、值保持一致，无论哪边生效结果都对。

---

## 改竞价

适用于匹配位、关键词、商品定向三种投放。

```
POST gw:spTarget/updateBid
Content-Type: application/x-www-form-urlencoded

shopId=711811&id=14313810921&bid=26
```

- `id` = **赛狐内部 target id**（`getAllTargetData` 行里的 `id`）
- `bid` = 数字，JPY

### 两个 target id 别混

| id | 示例 | 用途 |
|---|---|---|
| 内部 target id | `14313810921` | `updateBid` / `updateState` |
| Amazon targetId | `112163272021390` | 只读；**查建议价用它** |

实测：同类商品位 12.00 → 14.50，读回 14.50 ✅

### 怎么定位某个匹配位的内部 id

```python
rows = post("multiple/target/getAllTargetData", {
    "shopIdList": ["711811"], "campaignIdList": ["90709676806138"],
    "adType": "sp", "targetType": "auto",          # 必须显式 auto
    "startDate": D, "endDate": D, "pageNo": 1, "pageSize": 200,
    "fromSingle": True, "useAdvanced": False})
```

> ⚠️ `campaignIdList` 传 **Amazon campaignId（15 位）**。传内部 id（11 位）0 命中。

> ⚠️ 返回值里 `matchType` 常为 `null`。要判断哪一行是哪个匹配位，
> 靠 `searchAsin` 行的 `matchType`（`substitutes` → `asinSubstituteRelated`，`complements` → `asinAccessoryRelated`）
> 或建活动时响应里的 `matchTypeForAutoTarget`。

## 投放暂停 / 启用

```
POST gw:spTarget/updateState
Content-Type: application/x-www-form-urlencoded

shopId=711811&id=14313810921&state=paused
```

用于：只关掉某个烧钱不出单的匹配位，保留其余 3 位。

## 广告位加价

```
POST https://www.sellfox.com/api/cpcSPManage/campaign/updatePlacementAdjustment.json
Content-Type: application/x-www-form-urlencoded

shopId=711811&id=13804946433&placement=placementProductPage&value=20
```

- `id` = **活动内部 id**（不是广告位 id——广告位没有独立 id）
- `placement` 取值：`placementTop` / `placementRestOfSearch` / `placementProductPage` / `offAmazon`
- `value` = **0~900 的整数**（百分比）。`offAmazon` 不可调

gw 灰度路径：`gw:spCampaign/updatePlacementAdjustment`（参数相同）

实测：placementTop 10 → 15 读回 15.0 → 恢复 10 读回 10.0 ✅

### 什么时候该加

看 [03 广告位](03-读-广告表现.md#广告位) 的四行花费分布：哪个位的花费/订单比最好就加哪个。
**不出单的位不要加**（实测账户顶部 339 曝光 / 353 JPY / 0 单，就不该加）。

## 批量调价

```
POST gw:target/bid/batchAsyncUpdateBid
Content-Type: application/json

{"bidUpdateReq": {"bidType": "FIXED_BID", "adjustValue": "14.80"},
 "targetReq": { ...与 getAllTargetData 完全相同的筛选条件... }}
→ {"code": 0, "data": "6993315"}          ← data 是异步任务 id
```

进度轮询：

```
POST gw:target/task/list
{"shopId": "711811", "targetPageType": 1,
 "sourceAdCampaignId": "262736104900156", "pageNo": 1, "pageSize": 10}
→ rows[{id: 6993315, status: 3, targetObjectSize: 4, targetSize: 4, ...}]
```

`status=3` 即完成。

### ⚠️ JPY 取整坑（实测）

对 4 条投放批量设 `14.80` → **结果全部变成 15.00**。

- 日本站是整数币种，**批量调价的 `adjustValue` 会被取整**
- 而**行内单条** `spTarget/updateBid` 传 `14.50` 可以正常保存

**结论：需要精确到小数的出价，用单条 `updateBid`，不要用批量接口。**

### 批量接口的定位

适合"一次给几百条投放设同一个整数价"。用在少量精确调整上既慢又有取整风险。

> 另：批量广告位调整 `batchUpdatePlacementAdjustment` **参数契约未知**（试了 5 种形态全失败），
> 不要尝试。需要批量改广告位就只能循环调单条接口。

## 读回校验（每次改完必做）

| 改动 | 校验接口 | 期望 |
|---|---|---|
| 匹配位 bid | `multiple/target/getAllTargetData`（`targetType=auto`） | 4 行 `bid` = 新值 |
| 组默认竞价 | `GET /api/cpc/group/getInfo.json` | `defaultBid` = 新值 |
| 广告位加价 | `multiple/placement/getAllPlacementData` | 对应 `predicate` 行 `percentage` = 新值 |
| 活动状态 | `campaign/getAllCampaignData` 按 name 搜 | `state` / `servingStatusName` 符合预期 |

> 广告位接口改完返回 `code:0` 但**不回传新值**，必须再查列表确认。

## 建议的调价幅度（经验值，非接口约束）

| 场景 | 幅度 | 理由 |
|---|---|---|
| 出单且 ACOS 极低、曝光不足 | +30%，上限 +50% | 提价换曝光，风险极低 |
| 有花费 0 单、点击 ≥ 8 | −25% | 压 CPC 控亏损，不断流 |
| 零曝光 | 先查投放状态，不要盲目提价 | 可能是投放被暂停或预算已尽 |
| 单次调整上限 | ≤ 30% | 避免一次动太猛看不出因果 |

> 这些都是**策略层**的规则，不该写死在接口封装里。接口层只负责"能不能改、改多少合法"。
